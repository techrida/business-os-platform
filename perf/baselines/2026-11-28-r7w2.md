# Round 7 wave 2 performance baseline · 28 November 2026

**Prioritise mixed platform traffic and purchase-request submission.** At full volume, all nine platform request groups and all five procurement actions missed their server p95 limits. Approvals, sales and money met theirs. The largest job miss was procurement scanning, with a median p95 of **17.32 s** across the three runs. A verification upload that got as far as the scan queue always completed, but **22 of 51 reservations failed during the content PUT**, before enqueueing.

At the same arrival rate, verification alone had a 20.0 ms server p95 and completed all 60 uploads. Inbox reads still took 1,326.8 ms at p95 with only the read scenario active. The mixed results describe contention at sustained load.

These results describe commit `a66d76ace`. The later release update `7e7107e05` includes a department-head inbox matching change and a switch to nearest-rank percentile reporting. Neither change was present in the measured application or its reporter.

## What was measured

The target was release commit `a66d76ace` on 28 November 2026. Application services and k6 ran at ordinary priority on the isolated `bos-r7w2-p10` Compose project. Each workload ran three times, serially, against the same company. Each of the five Wave 2 scripts had a 60-second arrival window at one iteration per second per arrival scenario. Platform settings used its one continuous editor. These are the rates used in the unit runs. P-7 used a 12-second window. Repeated payments used disjoint ranges of the same issued-invoice manifest so each allocation could settle an unpaid invoice.

The 95th percentile (p95) is the time at or below which 95% of observations fall. The server table uses successful, flow-tagged application request logs. Each run cell gives **sample count / p50 / p95 / p99**, in milliseconds. Percentiles use the measured revision's linear interpolation over sorted observations. The final p95 is the middle of the three run p95s. The host and integrity table includes failed checks and dropped iterations. Server response times exclude unsuccessful requests, connection time and browser rendering. A small successful sample can therefore coexist with a failed workflow. The limits come from `.github/qa/flow-limits.json` and `perf/k6/thresholds.js` on the measured revision. Grades describe latency. Counts and failed checks show whether the workflow completed. Single actions target 50 ms and must stay below 80 ms.

The core seed ran 09:48:01–10:27:29 UTC (39 min 28 s). Full preparation through final dependency checks ended at 11:44:34 UTC (1 h 56 min 33 s from seed start). The company contained:

- 2,500 pending memo approvals for each of three roles, 5,000 leads and 20,000 activities.
- 5,000 quotations, 3,000 converted sales orders, 500 draft credit notes and 500 draft debit notes. These volumes supplement the core generator. Isolated opportunities were seeded with audit enabled, followed by ordinary application commands for the quotations, conversions and notes.
- 10,000 issued tax invoices from 28 November 2025 through 28 November 2026, 200 per customer across 50 customers, 5,000 submitted payments and 5,000 vendor bills.
- 2,000 confirmed serialized receipts and 2,000 issued purchase orders, plus the platform fixture's separate vendor invitation request. One procurement seed submission returned 503. Its existing draft was resumed to reach exactly 2,000 receipts.
- 562,827 audit events after the core seed and more than 1.08 million after completing the combined fixture. This is a larger audit history than the platform unit's 563,211 events.

All 2,000 purchase-order PDFs were clean before timing. Issued invoices created offline were queued on the normal render queue to clear the remaining invoice backlog. A temporary second worker and renderer helped drain that backlog. Both were removed, the ordinary worker was recreated, and all 10,000 issued invoices had clean PDFs before the first run. A real HTML-to-PDF conversion and a clean byte stream sent to ClamAV succeeded from the measurement worker. The stack used a local Mailpit email sink. No timed workloads or fixture writers overlapped. The shared test stack was not used.

The platform workload is a **combined stress test**. Each sidebar iteration reads 36 endpoints in sequence, while inbox/audit, verification, portal and settings scenarios run alongside it. An inbox sample can be a list, count or summary read. An upload sample can be either a reservation POST or a content PUT. An action labelled "scan-document" in the server table reads scan status. Queue timings measure the worker separately.

The CPU pressure and available memory were checked before every run. The collector waited for CPU pressure avg10 below 5% and at least 2 GiB of available memory before starting each window. CPU pressure required an extra 15-second wait before approvals run 3, database-read runs 2 and 3, and smoke run 1. All 24 primary windows started with 18 GiB available. PostgreSQL counters were reset immediately before each workload. Query rankings include application-role work during that window and can identify contention shared across routes. They do not assign every query to an individual HTTP request.

The host had an Intel Core i3-10105 (8 logical processors) and 31 GiB RAM. The database was PostgreSQL 16.16 with 256 MB shared buffers, 4 MB work memory and a 1 GiB container memory limit. API and worker each had 512 MiB. ClamAV was 1.5.4 with signature set 28194. The source build, not a previously tagged API image, supplied the API and worker.

Confirm the database counts, render backlog and dependency health. Invoke the k6 scripts directly in the disposable Compose project, since the convenience runner cleans up on exit. Set `K6_PERF_RATE=1` and `K6_PERF_DURATION=60s`. The money runs used invoice-array offsets 0, 100 and 200. Reset `pg_stat_statements` before every run, capture that run's server logs and queue events, and perform company cleanup once after the final run.

## Findings for the fix units

- **PERF-FU-1. The previous payment allocation tail did not recur.** Allocation p99 was 18.0, 19.8 and 20.6 ms across 181 successful requests. The earlier 529 ms outlier has no proven cause from these runs.
- **PERF-FU-2. Confirmed.** Sales VAT covers the current month. Receivables aging queried the current as-of date with no month-range parameter. Both reports met their latency targets.
- **PERF-FU-3. Confirmed.** All five procurement actions missed the 80 ms target. Start with purchase-request submission. Its successful median p95 was 5,953.4 ms and individual attempts also returned HTTP 503. The editor lookup in `apps/api/src/modules/procurement/requests/purchase-requests.service.ts` and recommender lookup in `sourcing.service.ts` call `audit.read_events`. That statement took 0.91–1.04 s per call under procurement load. Concurrent application transactions spent 224–260 cumulative seconds per run waiting for the tenant audit lock. Downstream actions have small successful samples because many chains stopped early.
- **PERF-FU-4. The earlier 9.3 s purchase-order render p95 did not recur in the median.** With all 2,000 seed PDFs ready, p95 was 1.80, 1.29 and 16.98 s (6, 4 and 6 jobs respectively). Every queued render completed. The third run still crossed 10 s, so seed backlog alone does not explain the tail.
- **PERF-FU-5. Confirmed under the mixed platform workload.** The grouped inbox list, count and summary median p95 was 14.89 s. The database list, count and summary statements each averaged over a second in run 1. The distinction between this combined workload and isolated reads matters for sizing a single page.
- **PERF-FU-6. Confirmed under the mixed workload.** Upload, access-policy save and filtered audit all missed their limits. The upload flow combines reservation and content transfer. The mixed run includes a settings editor continuously acquiring new revisions alongside the four paced scenarios.
- **PERF-FU-7. The previous widespread failure to finish already-queued scans was not reproduced.** The three platform runs made 51 verification reservations. All 29 successful content PUTs had queue-add and completion events. The other 22 content PUTs returned server-side 503. Seventeen versions stayed `awaiting_content`. Five stayed `quarantined` without a recorded digest. None of those 22 reached the queue. One completed scan took 100.06 s. Procurement scans also had a slow tail. Those tails warrant investigation separately from the failed verification uploads.

The lock is the **application's per-tenant audit-chain lock**. The statement fingerprint `2611122725302730362` matches `apps/api/src/platform/db/tx.ts:121`. PostgreSQL returned 1290458975687493864 for the hash of `audit.chain:` plus the perf tenant ID. During the later procurement window, `pg_locks` showed that exact key with one holder and three waiters. The offline fixture uses a separate session lock, `pg_try_advisory_lock(hashtext('bos-perf-data'))`, whose key was 770498851. The fixture writer had exited before measurement, and cleanup ran after measurement.

For example, at 11:44:53.070 UTC, API request `e9de48dc-8260-4c4b-a201-d1dc95086c0c` attempted the content PUT for version `5660061c-53f8-4ff8-a575-18a0b7f14858`. The two API log records reported "rolled back: database lock_timeout" and then "request errored", HTTP 503, 7,725 ms. The version remained quarantined without a SHA-256 digest, and its queue-add was absent. The upload path records the digest in a separate transaction before enqueueing (`documents.service.ts:876`). The stuck-scan sweeper selects only quarantined versions with a digest and detected type (`scan.processor.ts:409`). This is a failed upload that left partial state, distinct from a client timeout or a queued job waiting on ClamAV.

A platform sidebar iteration visits 36 endpoints. In run 1, 21 unpaged invoice-list responses transferred 94.47 MB, 21 quotation lists transferred 59.37 MB, 21 payment lists 29.38 MB and 21 sales-order lists 18.52 MB (decimal MB, measured from API response lengths). Together these four routes sent 201.74 MB. The mixed workload includes this traffic on every sidebar iteration. Its per-request p95 cannot stand in for the time to open one page. The known fan-out is at the HTTP layer. The aggregate SQL counters do not establish a per-row N+1 query pattern.

The arrival-rate comparison uses the previous platform unit's recorded command (`K6_PERF_RATE=1`, `K6_PERF_DURATION=12s`) and the unchanged platform scenario definitions. P-10 used the same rate for 60 s. Classifying successful requests by their inferred server arrival time (completion timestamp minus response time), first-12-second inbox p95 was 2.81, 2.52 and 5.32 s. Later-arriving inbox requests reached 15.79, 14.85 and 15.28 s. The first-12-second upload p95 was 2.38, 4.60 and 1.57 s, versus 16.90, 17.51 and 16.94 s later. These are computed subsets of the mixed windows, not independent replications of the earlier fixture.

## Coverage and interpretation

- All five Wave 2 scripts ran three times at full volume. The ordered host evidence below makes the workload boundaries explicit. The database-read, smoke and general-load scripts were also exercised against this company using its own machine identity.
- Queue rows use server-side added/completed event timestamps. For sales PDFs the table also shows the independent application interval from approval to a clean downloadable quotation. A fraction in the count column means completed/reserved or completed/source documents. Verification scan latency uses only the 29 jobs actually queued. The grades apply to those completions, and the separate 22 failed uploads remain failures. Purchase-order and procurement-scan pending counts were zero at the end of each run.
- Browser click-to-visible times, including the navigation-search result, were not collected. Navigation search filters locally and makes zero API calls. A browser duration cannot be inferred from this HTTP run. The sidebar row measures the API requests behind multiple pages. Email delivery was not timed. No live deployment or shared test-stack workflow was exercised.
- The `preview` and `write` rows are supporting memo actions. The table applies the single-action target to them. The older k6 client gates also set p95 at 200 ms for preview and 500 ms for write. The `enqueue-pdf` server row is the final quotation approval action. It passed both the configured PDF request limit and the 80 ms action limit. The credit and debit notes are measured separately. `allocate-payment` has the verify-payment single-action budget.
- Some p95s are based on fewer than ten successful requests. The per-run counts, state checks, failed PUTs and drops show where a percentile alone would overstate reliability. No application fixes or schema migrations are included.
